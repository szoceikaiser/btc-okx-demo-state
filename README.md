# Signed bootstrap template for encrypted OKX demo

Public repository: szoceikaiser/btc-okx-demo-state (ID 1430986303).
This local template prepares the manual workflow_dispatch bootstrap job with
condition true and environment okx-demo-bootstrap-disabled. The environment name
is not an execution switch. No schedule, artifact, cache, summary or credential
file is included. Final personal encryption and independent review are required
before publication. The execution manifest remains unapproved and root trust is
unbound; a prepared job condition alone grants no execution or trading authority.

The public manifest pins every allowed public file and the final ciphertext.
Workflow bytes contain no capsule hash; identical workflow bytes are inside the
authenticated encrypted runtime. Inner review bytes and all members are checked
before exclusive ephemeral restore and runtime checks. Linux CPython 3.12 x86_64
requires exact hashed wheels before offline installation; no source build or
dependency solving. Private runtime, seed and account evidence stay encrypted.

The encrypted runtime is prepared with the owner's verification public key.
The private offline signing seed stays with the owner and never enters the job.
A separate, explicit consent must name one already existing run, attempt one,
actor and standard ubuntu-24.04 hosted job. A later consent-only main commit
must have the running code commit as its sole parent and preserve every other
Git entry. Consent is never self-issued by the job. Fixed delivery rendezvous:
150 seconds; shared job budget:400 calls/240 seconds/32MiB. A durable exclusive
VM claim precedes every Git write, with deadline checks before every POST.
Unknown write outcomes and existing state heads prohibit another bootstrap.

Only the automatic same-repository job token and the existing personal AES data
key enter bootstrap. No exchange or market-data credentials are needed. No
market/account request, strategy pass or exchange write is authorized.
Run/recover/local-read remain behind their original gate. Ciphertext sizes,
commit times and workflow status remain public. Keep the existing AES data key
and the separate offline signing seed in their respective private backups.

## User-owned read quota

The agent preparation stage performs Git fetch/proof and browser preparation only;
it creates no anonymous REST ledger or quota baseline. The user arm process starts
the first and only rate-limit request and binds its own fixed40-request allowance.
Response headers and core counters must agree, enough quota and time must remain,
and QUOTA-OWNER.json binds the owner role to the session and actual code.

Agent and user execution contexts returned different reset timestamps in the
observed failure. No old context is adopted, rebased, deleted or replenished.
After the first user snapshot, every later response must retain the same reset
and monotonically consume the allowance. Existing ledgers and ambiguous transport
remain fatal. All150/240second limits, the110second signing floor and the private
signing process remain unchanged. No new operational run was needed for the
public snapshot reproduction and offline ownership tests.

## Before-arm operator rendezvous

Executing the personal arm command first enters a separate public waiting queue.
It creates only an immutable operator-wait marker and OPERATOR-WAITING evidence;
no REST quota, ARM clock, dispatch or signer starts. The mainchat, with the actual
workflow UI and all checks ready, releases this queue once through a session/code
bound OPERATOR-GO file and its atomic empty-directory ready signal. The user
process accepts only a fresh matching observation (at most five seconds old).
The queue expires after a fixed300seconds and cannot be resumed or retried.

Only then does the SAME user process establish its own first and only fixed40
read allowance and enter the unchanged120second ARM wait. A paste or chat-turn
delay before mainchat readiness therefore cannot spend that ARM clock. No old
ledger, marker, deadline, session or allowance is reset or adopted. All original
60second pre-dispatch,110second pre-signing,150second delivery and240second job
limits remain unchanged. The extra queue conveys no consent or runtime authority.

## Verify the first public follow-up before dispatch

After mainchat readiness and the user-owned initial quota snapshot, the SAME
user process performs one workflow-runs GET using the existing fixed allowance.
The actual route, quota policy and response shape must succeed before ARMED is
created. A code/session-bound READINESS-WARMUP receipt links this public response
to its immutable wire metadata. A failure here stops before any workflow dispatch.

Wire observations persist only HTTP status, selected public numeric quota headers,
request ID, byte count and body hash before acceptance. Failures also preserve
the rejection phase, exception type and numeric system or TLS verification code.
No raw body, credentials, exception message or signing input is recorded. Such
observations confer no authority and cannot repair an incomplete accepted ledger.
No network request is retried; all forty-call, response, time and consent limits
remain unchanged. This is a defensive preflight/diagnostic correction: the failed
run response itself was not saved, and later successful public GETs do not prove
the original cause. The existing failed attempts remain consumed.
